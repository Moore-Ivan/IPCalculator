# IPCalculator 缺陷修复报告

> 记录两轮系统性缺陷审查中发现的问题：发现过程、根本原因、修复方案与验证结果，供未来回归参考。
>
> - 第一轮（v1.5.6 → v1.5.7）：核心计算逻辑审查，修复 5 项（提交 `9686603`）。
> - 第二轮（v1.5.7）：全项目审查（UI 层 / 服务层 / 基础设施工具），修复 7 项。
>
> 审查方法：代码静态审查 + 最小复现验证（javac 独立编译 / 反射调用私有方法构造用例）+ 既有单元测试回归（JUnit）+ Gradle 全量编译。

---

## 第一轮：核心计算逻辑（提交 9686603，v1.5.7）

### 1. IPv4 路由汇总对嵌套/混合前缀网段直接报错

- **发现过程**：审查 `SubnetCalculator.summarize()` 时，用 `10.0.0.0/8 + 10.0.0.0/24` 手工推演，本应汇总为 `10.0.0.0/8`，实际抛出"需要多个汇总路由"。
- **根本原因**：仅用各网段网络地址的 XOR 求公共前缀。嵌套网段 XOR 为 0 → 候选超网为 /32，包含性检查必然失败。但任意网段集合必然存在超网（最坏 /0），直接报错属于逻辑错误。
- **修复方案**：从 XOR 推导的候选前缀开始，若包含性检查失败则逐级减小前缀（放大超网），直至全部包含，下限 /0。
- **验证**：嵌套、混合、不相邻等多组用例全部通过；与预期人工汇总结果一致。

### 2. IPv6 路由汇总存在同样缺陷

- **发现过程**：与上一条同源，`2001:db8::/32 + 2001:db8::/48` 触发同样的错误异常。
- **根本原因**：`summarizeIPv6()` 与 IPv4 版本完全相同的 XOR 缺陷。
- **修复方案**：同上，逐级降级前缀至 `::/0`。
- **验证**：嵌套前缀用例通过。

### 3. 6to4 地址嵌入的 IPv4 提取错误（恒为 0.0.0.0）

- **发现过程**：输入 `2002:c000:0204::`（内嵌 192.0.2.4），地址类型解析显示嵌入 IP 为 `0.0.0.0`。
- **根本原因**：`addr.and(0xFFFFFFFF)` 取的是地址最低 32 位（接口标识符），而 6to4（RFC 3056）的 IPv4 位于第 16–47 位。
- **修复方案**：改为 `addr.shiftRight(80).and(0xFFFFFFFF)`。
- **验证**：`2002:c000:0204::` → `192.0.2.4`，与 RFC 3056 定义一致。

### 4. IPv6 多播 P 标志位（前缀标志）解析错误

- **发现过程**：解析 `ff32::`（RFC 3306 基于前缀的多播地址）时显示 `P: 否`。
- **根本原因**：多播标志 4 位结构为 `0|R|P|T`（R=0x4，P=0x2，T=0x1，RFC 4291/3306/3956），原代码用 `flags & 0x04` 判断 P，实际取到的是 R 位；且"否"分支的文案描述的是 R 位（嵌入式 RP）含义，进一步误导。
- **修复方案**：掩码改为 `0x02`，并修正"否"分支文案为"否 (非基于前缀)"。
- **验证**：`ff32::` 显示 `P: 是`；`ff02::1` 显示 `P: 否`。

### 5. getPrefixForHosts 对非法主机数静默返回（IPv4 + IPv6）

- **发现过程**：代码审查发现 `if (hosts <= 1) return 32` 写在 `if (hosts < 1) throw` 之前，后者永远不可达（死代码）。
- **根本原因**：条件顺序错误，`0` / 负数被 `hosts <= 1` 分支吞掉，静默返回 /32（IPv6 同样问题返回 /128），调用方无法感知非法输入。
- **修复方案**：调整顺序，`hosts < 1` 先抛 `IllegalArgumentException("主机数必须至少为 1")`；IPv6 版本（含 null 检查）同样处理。
- **验证**：`0`、`-5`、（IPv6）`null` 均抛异常；`1→/32`、`2→/31`、`100→/25` 行为不变。

## 第二轮：UI 层 / 服务层 / 基础设施（v1.5.7）

### 6. 更新检查器信任任意 TLS 证书（安全漏洞）

- **发现过程**：审查 `UpdateChecker` 网络代码时发现自定义 `FallbackTrustManager`，其 `checkServerTrusted()` 在系统证书校验失败后**不抛异常直接返回**，即回退为信任任意证书。
- **根本原因**：为规避精简 JRE 证书库不完整导致的握手失败，引入了"回退到信任所有证书"逻辑。注释称"仅连接已知 GitHub 端点所以安全"，不成立——信任管理器对 TLS 握手对端不做来源区分，中间人可拦截连接。更严重的是：同一条 `openConnection()` 路径还用于**下载并执行安装程序**（`downloadAndInstall` → `launchInstaller`），攻击者可借此替换安装包植入恶意程序。
- **修复方案**：删除 `FallbackTrustManager`，`SSLContext.init(null, null, null)` 使用 JVM 默认信任管理器（保持完整证书链校验）；保留 TLSv1.3 协议强制。构建脚本 `prepareJre` 已将完整 `cacerts` 拷入 jlink JRE，正常证书校验不受影响。
- **验证**：编译通过；更新检查/下载路径代码评审确认不再存在信任回退分支。

### 7. 网络检查失败后 24 小时内不再自动检查更新

- **发现过程**：审查 `checkSync()` 时发现"上次检查时间"在 `conn.connect()` 之后、`getResponseCode()` 之前写入。连接超时、403 限流、解析失败等任何异常路径都已消耗掉本次检查标记。
- **根本原因**：时间戳写入位置过早，失败请求与成功请求同等对待。
- **修复方案**：将写入移到成功获取有效 Release 信息之后（HTTP 200 且 JSON 解析成功）。
- **验证**：代码评审确认失败路径不再更新时间戳，下次启动仍会自动重试。

### 8. 掩码转换器接受非连续掩码

- **发现过程**：推演 `decimalToPrefix("255.0.255.0")`：每个 octet（255/0/255/0）单独看都是合法掩码值，逐段校验全部通过，按 `bitCount` 求和返回前缀 16。同理 `0.255.0.0` → /8、`255.255.0.255` → /20 均被接受。
- **根本原因**：只做了"逐 octet 合法性"校验，缺少"掩码必须从高位起连续"的整体校验；`255.0.255.0` 并非合法子网掩码。
- **修复方案**：将 4 个 octet 组装为 32 位数值，与该前缀对应的标准掩码 `(0xFFFFFFFFL << (32 - prefix)) & 0xFFFFFFFFL` 做数值比对，不一致即抛"不是有效的子网掩码"；顺带为非数字段（如 `255..0.0`）补充了明确的中文错误信息（原先透出 JDK 英文异常文本）。
- **验证**：反射调用 `decimalToPrefix` 跑 14 组用例（含 7 组合法、7 组非法），全部符合预期；合法掩码 `0.0.0.0`（/0）与 `255.255.255.255`（/32）边界正确。

### 9. 进制转换器接受带符号输入并产生乱码结果

- **发现过程**：`new BigInteger(input, base)` 会接受 `+`/`-` 前缀。输入 `-10101010`（二进制）→ 负数 → `toString(2)` 得 `-10101010`，`formatBinary` 补齐 4 的倍数位后产生 `000-10101010` 之类的错乱输出；八/十六进制前缀拼接同样错乱。
- **根本原因**：输入校验缺失——工具语义上只支持非负整数，而 `BigInteger` 解析比预期宽松。
- **修复方案**：`convert()` 入口拒绝以 `+`/`-` 开头的输入，提示"不支持正负号，请输入非负数值"。
- **验证**：带符号输入显示错误提示；正常数值转换结果不变。

### 10. 配置/历史 JSON 损坏导致应用启动崩溃

- **发现过程**：审查 `ConfigStore` 静态初始化时发现 `loadSettingsFromJson`/`loadHistoryFromJson` 只捕获 `IOException`；`gson.fromJson` 对损坏文件抛出的 `JsonSyntaxException`（RuntimeException）会从 `static {}` 块逃逸。
- **根本原因**：异常处理范围不足。一旦 `config/settings.json` 或 `config/history.json` 被外部编辑损坏（或版本升级后结构变化），类初始化失败 → `ExceptionInInitializerError` → 应用启动即崩溃，且每次启动都崩溃无法自愈。
- **修复方案**：两个加载方法改捕 `Exception`，损坏时记日志并回退到默认配置/空历史，下次保存自动修复文件。
- **验证**：编译通过；损坏 JSON 场景代码评审确认走回退分支。附带修复：`NumberBaseConverter.loadSavedValues` 原来用未捕获的 `Integer.parseInt` 读取损坏的进制配置会导致窗口打不开，改用 `ConfigStore.getSetting(key, intDefault)` 重载并增加 0..3 边界回退。

### 11. CalculationWorker 并发访问非线程安全 WeakHashMap

- **发现过程**：`workerMessages` 在 `doInBackground`（多个 worker 线程并发 `put`）与 EDT（`propertyChange` 读取、`done()` 删除）之间共享，声明为裸 `WeakHashMap`。
- **根本原因**：`WeakHashMap` 非线程安全，并发写入可导致内部结构损坏（如 `CorruptedHashMapException`/死循环），且无同步保障可见性。概率低但属真实数据竞争。
- **修复方案**：`Collections.synchronizedMap(new WeakHashMap<>())` 包装（该 Map 只做单键 put/get/remove，无需额外锁）。
- **验证**：Gradle 全量编译 + 既有测试通过；并发语义评审确认。

### 12. F11 全屏切换完全失效

- **发现过程**：审查 `SubnetGUI.toggleFullscreen()` 发现其在已显示的窗口上调用 `setUndecorated(true/false)`。
- **根本原因**：AWT 规定 `Frame.setUndecorated()` 只能在窗口不可显示（not displayable）时调用，否则抛 `IllegalComponentStateException`。应用窗口显示后按 F11 必然抛异常，全屏功能从未生效（异常仅打印到控制台，用户侧表现为"按了没反应"）。
- **修复方案**：删除两处 `setUndecorated()` 调用，直接使用独占全屏 `setFullScreenWindow()`；退出时恢复保存的窗口边界。独占全屏模式下 decorations 不渲染，视觉效果不变。
- **验证**：代码评审确认不再有对可显示窗口的 decoration 修改；进入/退出路径均为受支持的 API 用法。

### 13. IPv6 大子网分页被截断到 Integer.MAX_VALUE，后一半子网无法显示

- **发现过程**：审查 `IPv6Calculator.subnetByPrefixPaged()` 发现 `long totalCount = maxSubnets.min(BigInteger.valueOf(Integer.MAX_VALUE)).longValue()`。对 `2001:db8::/32 → /64`（共 2^32 = 4,294,967,296 个子网）总数被静默截断为 2^31-1。
- **根本原因**：为避免 `long` 溢出用 `min(Integer.MAX_VALUE)` 钳制，但钳制值直接当作"总数"使用——超出部分永远无法翻页到达，属于静默数据丢失；且与 `getSubnetCount()` 返回的真实总数（UI 显示"总计 4294967296"）互相矛盾。
- **修复方案**：页起始偏移与页长全部用 `BigInteger` 计算：`start = BigInteger.valueOf((pageNum-1) * pageSize)`，`count = min(pageSize, maxSubnets - start)`（结果必 ≤ pageSize，可安全转 int），循环生成当页子网。
- **验证**：最小复现用例（javac 独立编译运行）：
  - `2001:db8::/32` → /64，第 1 页（pageSize=100）100 条 ✓
  - 第 21474837 页（起始 2147483600，跨过旧截断点）96 条，末条 `2001:db8:ffff:ff60::/64` ✓
  - 超出总量的页返回空列表 ✓
  - 普通小分页第 2 页首条 `2001:db8:0:32::/64` ✓（与修复前行为一致）

## 经验总结

1. **安全红线**：任何"证书校验失败就放行"的回退逻辑都是漏洞，尤其当同一条网络路径承担可执行内容分发（更新包下载）时。精简 JRE 应通过拷入完整 `cacerts` 解决证书问题，而不是降低校验标准。
2. **副作用位置**：时间戳/状态标记的写入应放在操作**成功之后**，失败路径不应消耗重试机会。
3. **BigInteger 与 long 边界**：IPv6 数量级（最大 2^128）下，任何 `long`/`int` 钳制都是潜在的数据丢失点，页边界等"偏移量"语义的值必须全程 BigInteger。
4. **死代码即缺陷信号**：不可达的校验分支（如写在 `<=` 之后的 `<` 抛错）通常意味着条件顺序已经出错。
5. **Swing/AWT API 契约**：`setUndecorated` 等带"displayable 限制"的方法要在窗口可见前调用；运行期异常若只打印到控制台，功能失效对用户不可见。
6. **静态初始化必须自愈**：从磁盘加载的任何数据都可能损坏，`static {}` 中的解析失败应回退默认值而非让类初始化失败。
